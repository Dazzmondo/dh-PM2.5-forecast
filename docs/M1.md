# Six-Hour Urban PM2.5 Forecasting Across Ireland and Europe

**Milestone 1: data storage, versioning, preprocessing and splits**

## Project overview

This project builds an end-to-end AI/ML system that forecasts the **3-hour mean PM2.5 concentration 6 hours ahead** at urban air-quality monitoring stations in Ireland and Europe. Historical measurements from official sources are stored in Google Cloud Storage (GCS), cleaned into one common dataset, turned into features and split chronologically, ready for model training in later milestones.

**Main question:** Can machine learning accurately forecast PM2.5 concentrations 6 hours ahead across different Irish and European cities using historical air-quality measurements?

**Secondary questions:**
1. Can a model trained across several cities generalise to a city not seen during training?
2. Does including geographically and environmentally diverse cities improve or affect generalisation? (A hypothesis to be tested, not an assumption.)

**Planned models:** Persistence baseline → Linear Regression → XGBoost → PyTorch GRU/LSTM (optional). Milestone 1 covers the data pipeline only; no models are trained yet.

## 1. Raw data storage (1.0 point)

**Where:** all original source files are kept, unchanged, in a **Google Cloud Storage (GCS)** bucket under `raw/`, in one folder per source, city and station. The bucket is in the EU multi-region.

**Why GCS:** the raw data are historical files that are read in batches and never updated transactionally, so durable, scalable object storage is the right fit. Keeping the raw files untouched also follows the data-lake principle: if a preprocessing decision turns out to be wrong, the processed data can be regenerated without downloading everything again.

```text
gs://<bucket>/
├── raw/          original files, never edited
│   ├── epa/      cork, dublin/(dublinKilmainham, dublinRathmines), galway, limerick, waterford
│   ├── uk_air/   belfast, derry, london/(londonBloomsbury, londonKensington)
│   └── eea/      athens/(athensAristotelous, athensParaskevi), copenhagen,
│                 madrid/(madridCuatroCaminos, madridEscuelasAguirre),
│                 paris/(parisGennevilliers, parisSaintDenis)
├── processed/    canonical/, three_hour/, features/, splits/   (Section 2)
├── manifests/    raw_files.jsonl, dataset_versions.jsonl       (Section 4)
├── metadata/     station_reference.csv
└── models/       planned for later milestones
```

**Upload script:** [`upload_raw_data.py`](src/upload_raw_data.py) mirrors the local `raw_data/` folder (same layout) into `raw/`:
- It creates the bucket if it does not exist (EU location, uniform bucket-level access, object versioning on). If an existing bucket has versioning off, it switches it on.
- It computes a SHA-256 checksum of each file *before* uploading. A file already in the bucket with the same checksum is skipped; a file whose content changed is uploaded again as an update, and the earlier copy is kept by bucket versioning.
- It adds one record per uploaded file to `manifests/raw_files.jsonl` (Section 4) and finally compares the number of local files with the number of objects under `raw/`.

## 2. Processed data storage and file formats (1.0 point)

Processed data are stored in the same bucket under `processed/`, always as **Apache Parquet**. Raw files keep their original formats (CSV for EPA Ireland and UK-AIR, Parquet for EEA) and the manifests are JSON Lines.

| Path in `processed/` | Contents | Rows |
|---|---|---:|
| `canonical/canonical_hourly.parquet` | Hourly PM2.5 for all 17 stations in one schema, UTC timestamps | 943,899 |
| `three_hour/three_hour_aggregated.parquet` | 3-hour mean blocks with the number of valid hours | 318,791 |
| `features/pm25_features.parquet` | Features and target for every usable row, plus the `split` label (the 22 columns of the local feature table + `split`) | 285,551 |
| `splits/train/train.parquet` | Training rows | 123,364 |
| `splits/dev/dev.parquet` | Development rows | 31,192 |
| `splits/test/test.parquet` | Final test rows | 25,921 |
| `splits/held_out/held_out_test.parquet` | 2025 rows of the held-out (unseen) cities | 13,362 |
| `splits/future_update/` | 2026 data for the Milestone 4 update demo | empty until 2026 data are added |

Rows labelled `excluded` (91,712) appear only in `pm25_features.parquet`.

**Why Parquet:** the data are structured time series with many numeric columns that are read repeatedly for analysis and training. Parquet is columnar (only the needed columns are read), compressed, keeps data types (timezone-aware timestamps, floats, integers) and is read directly by pandas, PyArrow and BigQuery. It is a storage choice, separate from the data type: PM2.5 is numerical time-series data whichever format holds it.

**Store script:** [`store_preprocessed_data.py`](src/store_preprocessed_data.py) uploads each stage with its row count, uploads `metadata/station_reference.csv`, stops with a clear message if an earlier stage has not been run, and appends a version record to `manifests/dataset_versions.jsonl` (Section 4).

## 3. Database / object storage decision (0.5 point)

Different workloads use different tools; nothing is forced into one database.

| Option | Decision | Reason |
|---|---|---|
| GCS object storage | **Used**: the authoritative store for raw data, processed Parquet, manifests and metadata | Historical files read in batches, no transactional updates, durable and scalable |
| Parquet files | **Used** for all processed data | Columnar, compressed and typed; fast analytical reads with pandas and PyArrow |
| BigQuery | **Not used for now** (optional later) | About 319k three-hour rows (944k hourly) are analysed with pandas in seconds, while BigQuery adds setup (datasets, load jobs, IAM). It will be reconsidered later based on workload and educational value |
| Cloud SQL / PostgreSQL | **Not used** | There are no transactional updates or CRUD workloads; the work is batch ingestion, analysis, feature generation and training |
| Sharding / partitioning | **Not needed** | The data stay manageable as single Parquet files; partitioning by year or station can be added later without changing the raw layout |
| Feature store | **Not used** | Feature definitions live in version-controlled code (`feature_extraction.py`); training-serving consistency will be handled in Milestone 4 by reusing the same code |

## 4. Data versioning (0.5 point)

Source organisations can publish revised or corrected measurements, so versions are explicit and nothing is overwritten silently.

**Raw files.** Bucket object versioning is on, and every uploaded file gets one record in `manifests/raw_files.jsonl`:

| Field | Meaning |
|---|---|
| `local_path`, `gcs_path` | Where the file was on the machine and where it went in the bucket |
| `source` | First folder: `epa`, `uk_air` or `eea` |
| `checksum_sha256` | Hash of the file contents, computed before upload |
| `size_bytes`, `file_modified_utc` | File size and last-modified time (the best stand-in for download time) |
| `upload_timestamp_utc` | Time of upload |
| `pipeline_version`, `git_commit` | Code version (`config.py`); the commit gets a `-dirty` suffix if tracked files have uncommitted changes |

**Processed datasets.** Each run of `store_preprocessed_data.py` appends one line to `manifests/dataset_versions.jsonl`:

| Field | Meaning |
|---|---|
| `dataset_run_id`, `created_timestamp_utc` | Identify the run (UTC timestamps) |
| `pipeline_version`, `preprocessing_version`, `feature_version` | Version labels |
| `git_commit` | Code version that produced the data |
| `raw_data_version` | SHA-256 of `raw_files.jsonl`: a fingerprint of exactly which raw files existed |
| `station_reference_sha256` | SHA-256 of `metadata/station_reference.csv` |
| `row_counts`, `config` | Rows per split; the settings used (rolling window, forecast horizon, minimum valid hours, completeness threshold) |
| `outputs` | For every file written: GCS path, SHA-256, size and rows |

This gives the lineage **raw data version → preprocessing version → feature dataset version → (from Milestone 2) training run → model**, so the question "which exact data, preprocessing code and feature definitions produced this model?" can be answered.

## 6. Data split / validation strategy (2.0 points)

The data are time series, so the split is **chronological**: a random split would let future observations influence model development.

| Period | Years | Used for |
|---|---|---|
| Training | 2018–2023 (Irish stations: 2022–2023) | Fitting model parameters; time-aware cross-validation may be used inside this period |
| Development | 2024 | Comparing models, tuning hyperparameters, selecting features, early stopping |
| Final test | 2025 | Untouched until final evaluation; never used to choose a model, hyperparameters, features or window length |
| Future update | 2026 | Reserved for the Milestone 4 "new data → retrain → compare with v1" demo |

Approximate shares (training / development / test): non-Irish stations 75% / 12.5% / 12.5%; Irish stations 50% / 25% / 25%, because they only have data from 2022. The result is 285,551 usable rows, 123,364 of them for training, far above the course minimum of 10,000 samples (counts in Section 2).

**Geographic holdout.** Three cities are held out: **Derry** (GB1060A), **London** (Bloomsbury GB0566A, N. Kensington GB0620A) and **Paris** (Gennevilliers FR04002, Saint-Denis FR04058). They are excluded from training and model selection, and only their 2025 rows (`held_out_test`) are used to measure generalisation to unseen cities. This gives two evaluation dimensions: known cities in later years (temporal) and completely unseen cities (spatial). Held-out cities stay unseen across all source systems.

**Cross-validation.** Random k-fold cross-validation over the whole dataset is not used. If cross-validation is needed it will be time-aware and restricted to the training period; the 2024 and 2025 data stay outside it.

**Leakage prevention**
- Lag and rolling features use only the block that has just finished and earlier blocks; the target block never enters a feature.
- A row is labelled only if its input block and its target block (6 hours later) fall in the same period. A row whose input is in late December 2023 but whose target is in January 2024 is `excluded` (56 rows), so no training label comes from the development year. New Year inside the training period is not a boundary.
- Held-out stations never enter train, dev or test; the script stops if one does.
- Steps that learn from data (scaling, encoding, imputation values, feature selection, hyperparameter tuning) will be fitted on training data only and applied unchanged to dev and test (Milestone 2). Deterministic steps (timestamp parsing, station mapping, duplicate removal, 3-hour aggregation) learn nothing from the data, so they run before the split.

**Implementation:** [`create_splits.py`](src/create_splits.py) gives every row a `split` label: `train`, `dev`, `test`, `held_out_test`, `future_update` or `excluded`. Training starts in each station's first available year (`availability_start` in `station_reference.csv`, never before 2018), which is how the Irish stations start in 2022 without a special rule. The script stops, writing nothing, if a held-out code is not in `station_reference.csv`, if a held-out station is missing or has no 2025 rows, or if any held-out row ends up in train, dev or test.

```python
# src/create_splits.py (excerpt from assign_splits)
in_period = period_of(df["block_start_utc"].dt.year, train_start_year)           # period of the input block
target_period = period_of(df["target_block_start_utc"].dt.year, train_start_year)  # period of the block predicted
same_period = in_period == target_period  # False only for rows straddling a split boundary
is_held_out = df["station_id"].isin(HELD_OUT_STATIONS)

# np.select takes the FIRST condition that is true, so the ORDER below matters.
conditions = [
    same_period & (in_period == "future"),                  # 2026 rows: kept for the update demo
    same_period & is_held_out & (in_period == "test"),      # an unseen city's 2025 rows: the unseen-city test
    is_held_out,                                            # every other row of an unseen city: unused
    same_period & (in_period == "test"),
    same_period & (in_period == "dev"),
    same_period & (in_period == "train"),
]
choices = ["future_update", "held_out_test", "excluded", "test", "dev", "train"]
```

## 7. Feature description (1.0 point)

| Feature | What it is | Type |
|---|---|---|
| `pm25_current` | Mean PM2.5 of the 3-hour block that has just finished when the forecast is made | Continuous, µg/m³ |
| `pm25_lag_1`, `pm25_lag_2`, `pm25_lag_3` | Mean PM2.5 of the 1st, 2nd and 3rd block before the current one (3, 6 and 9 hours earlier) | Continuous, µg/m³ |
| `pm25_rolling_mean`, `pm25_rolling_std` | Mean and standard deviation of the last 8 blocks (24 hours), including the current block | Continuous, µg/m³ |
| `time_block` | 3-hour slot of the day in station-local time: 0 = 00:00–02:59 … 7 = 21:00–23:59 | Integer 0–7 |
| `day_of_week` | Local day of the week, 0 = Monday … 6 = Sunday | Integer |
| `month` | Local calendar month, 1–12 | Integer |
| `season` | Meteorological season: Dec–Feb winter, Mar–May spring, Jun–Aug summer, Sep–Nov autumn | Categorical |
| `city`, `country` | City and country of the station (from `station_reference.csv`) | Categorical |
| `latitude`, `longitude` | Station coordinates | Continuous |
| `target_pm25` | Mean PM2.5 of the block 2 blocks (6 hours) after the current one | Continuous, the target |

The feature table also holds these bookkeeping columns: `station_id`, `timezone`, `block_start_utc`, `local_timestamp`, `pm25_3h_mean`, `valid_hours`, `target_block_start_utc` and, after the split, `split`.

**How the features are built** ([`feature_extraction.py`](src/feature_extraction.py)):
- A forecast is issued *after* a 3-hour block has finished, so that block's mean (`pm25_current`) is a known input. Nothing from the target block or later enters any feature.
- Blocks are fixed 3-hour windows on the UTC clock, so "2 blocks ahead" is exactly 6 hours all year, even on daylight-saving change days. Only the time-of-day, weekday, month and season labels use the station's local time (IANA time zone from `station_reference.csv`).
- Each station is first placed on a complete 3-hour grid, so a missing block shows up as a gap instead of silently joining two distant blocks.
- A row needs the current block, all 3 lags, all 8 rolling blocks and the target to be valid. Rows that fail are dropped and nothing is imputed (33,240 rows dropped, 285,551 remain).
- Weather, PM10, NO2 and O3 are left out of the first version to focus on what the PM2.5 record itself can predict.
- Station and city identity could let a model memorise places, which matters for the unseen-city question, so whether they stay model features is a Milestone 2 decision. Latitude and longitude are the more generalisable alternative.

```python
# src/feature_extraction.py (excerpt from add_lag_rolling_and_target)
for k in (1, 2, 3):
    df[f"pm25_lag_{k}"] = grouped.shift(k)   # the value k blocks (3k hours) earlier
# mean / std of the last 8 blocks including this one; min_periods=8 gives NaN unless all 8 blocks have a value
df["pm25_rolling_mean"] = grouped.transform(
    lambda s: s.rolling(ROLLING_WINDOW_BLOCKS, min_periods=ROLLING_WINDOW_BLOCKS).mean())
df["pm25_rolling_std"] = grouped.transform(
    lambda s: s.rolling(ROLLING_WINDOW_BLOCKS, min_periods=ROLLING_WINDOW_BLOCKS).std())

# the grid is gap-free, so shifting by N rows is exactly N blocks
df["target_pm25"] = grouped.shift(-TARGET_HORIZON_BLOCKS)   # the value 2 blocks (6 h) LATER: what the model predicts
df["target_block_start_utc"] = df["block_start_utc"] + pd.Timedelta(hours=3 * TARGET_HORIZON_BLOCKS)
```

## 10. Reproducibility of preprocessing (1.5 points)

Everything below is code in `src/`, run in the order shown in "Pipeline at a glance". The same raw files and the same settings give the same processed dataset.

| # | Step | What happens | Script |
|---|---|---|---|
| 1 | Parse and match | Each CSV or Parquet file is read and matched to a station: EPA and UK-AIR by their folder, EEA by the station code inside the file. A file that matches nothing stops the run. | `canonicalize_raw_data.py` |
| 2 | Standardise timestamps | Every source is converted to hourly UTC timestamps labelled by the start of the hour (table below). | `canonicalize_raw_data.py` |
| 3 | Source quality rules | EEA rows count only if their `Validity` flag is 1, 2 or 3 (others become missing). Non-hourly EEA files are skipped. Empty EPA placeholder rows stamped off the hour are dropped. UK-AIR uses the single "PM2.5 particulate matter" column and checks the site name in each file's header. | `canonicalize_raw_data.py` |
| 4 | Duplicates | Identical duplicate station-hours are dropped. Different values for the same station-hour stop the run instead of being resolved by row order. | `canonicalize_raw_data.py` |
| 5 | Quality checks | Completeness per station and year against the hours expected from `availability_start`, duplicates, negative values and values above 500 µg/m³. Reports only; nothing is removed. | `validate_data_quality.py` |
| 6 | Aggregate | Fixed 3-hour UTC blocks; a block's mean is kept only if at least 2 of its 3 hours are valid, otherwise it is missing (never filled). | `aggregate_to_3hour.py` |
| 7 | Features and target | Complete 3-hour grid per station, then time features, 3 lags, 8-block rolling mean and standard deviation, and the target 2 blocks ahead (Section 7). | `feature_extraction.py` |
| 8 | Split | Chronological labels and the held-out cities (Section 6). | `create_splits.py` |
| 9 | Store and version | Parquet files to GCS and a dataset record in `dataset_versions.jsonl` (Sections 2 and 4). | `store_preprocessed_data.py` |

**Timestamp conventions**

| Source | Label in the file | Time zone | Action |
|---|---|---|---|
| EEA hourly | interval start | UTC+1 (EEA converts every country) | subtract 1 h |
| UK-AIR | hour ending (the day's last hour is written `24:00`) | GMT | subtract 1 h |
| EPA Ireland | hour ending | UTC (both inferred from the data, not documented) | subtract 1 h |

**Parameters** (the values are recorded in each dataset record, Section 4)

| Parameter | Value | Set in |
|---|---|---|
| Block length | 3 hours, fixed windows on the UTC clock | `aggregate_to_3hour.py` |
| Minimum valid hours per block | 2 of 3 (`MIN_VALID_HOURS`) | `aggregate_to_3hour.py` |
| Lags / rolling window / horizon | 1, 2, 3 blocks / 8 blocks (24 h) / 2 blocks (6 h) | `feature_extraction.py` |
| Completeness threshold | 75% valid hours per station and year (a diagnostic, not a filter) | `validate_data_quality.py` |
| Study window for the checks | 2018-01-01 to 2025-12-31 | `validate_data_quality.py` |
| Split years and held-out stations | Section 6 | `create_splits.py` |

## Known limitations and open decisions

- **EPA data are provisional**, and their hour-ending label and UTC time zone are inferred from the data rather than documented. Both are flagged in the code.
- **Irish stations have only two years of training data** (2022–2023), less depth for time-aware cross-validation. The effect on model performance will be measured.
- **Gaps:** Kilmainham 2025, Copenhagen 2021 and 2025, London Bloomsbury 2021–2022 (table in Section 10). How stations with no 2025 data are handled in the evaluation is open.
- **Negative readings** (5,663) are kept and reported for now; whether to set them to missing, clip them or keep them is a Milestone 2 decision.
- **To be settled in Milestone 2 using training and development data only:** whether the 2-of-3 valid-hours rule and the 8-block window are right, how much missing data is tolerable, whether station and city identity are model features, and the sequence length for the optional GRU/LSTM.

## Reproduce it yourself

1. Clone the repository and install Python 3.10 or newer.
2. Download the raw files (Section 5) and file them under `raw_data/` as shown there.
3. Create a virtual environment and run `pip install -r requirements.txt`.
4. Sign in to Google Cloud (`gcloud auth application-default login`) and set `GCP_PROJECT_ID` and `GCS_BUCKET_NAME`. The upload script creates the bucket itself.
5. From the repository root, run the seven scripts in order:

```
python src/upload_raw_data.py
python src/canonicalize_raw_data.py
python src/validate_data_quality.py
python src/aggregate_to_3hour.py
python src/feature_extraction.py
python src/create_splits.py
python src/store_preprocessed_data.py
```

[`SETUP_GUIDE.md`](SETUP_GUIDE.md) has the full walkthrough (PowerShell and bash commands, expected output of every script, troubleshooting).
